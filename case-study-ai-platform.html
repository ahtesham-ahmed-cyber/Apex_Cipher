Illustrative concept

Enterprise AI knowledge platform

A retrieval-augmented assistant for a regulated operations team: grounded answers, citation trails, evaluation harnesses, and a review workflow that keeps people in control of decisions with real consequences.

  • Applied AI
  • Retrieval
  • Evaluation
  • Governance
Concept type
Retrieval-augmented assistant with human review
Primary disciplines
AI engineering, backend services, evaluation
Illustrative timeframe
Assessment, then staged delivery over multiple increments
Nature of this document
Demonstration concept — not a real client engagement

This case study is a demonstration concept. It does not describe a real client, and no specific company outcomes, statistics, or testimonials are implied. The architecture, practices, and trade-offs described are the ones we would bring to a comparable engagement.

Context

The concept is set inside a regulated operations function: a department whose daily work involves answering questions that are governed by internal policy, external regulation, and precedent from previous cases. The answers matter. A wrong answer can lead to a compliance finding, a customer dispute, or a decision that has to be unwound later.

The team that would use the system is experienced. They are not looking for a system to make decisions for them. They want faster access to the material they already trust, and a way to move from a question to a documented answer without manually searching across several internal tools.

Problem

The knowledge needed to answer a typical query is distributed across policy documents, previous case records, an internal wiki that is only partially maintained, and a small number of subject-matter experts who are consistently over-asked. Finding the relevant material takes time, and the resulting answer is difficult to document in a way that satisfies the review requirements.

A general-purpose chatbot would not help here, and could make the situation worse. It would produce answers that look authoritative but cannot be traced to a source, which is unacceptable in a context where an auditor will ask where the answer came from.

Constraints

Several constraints shaped the concept from the outset. These were treated as design inputs, not obstacles.

  • Traceability. Every answer must be reconstructable: which passages were used, which version of the source, and which reasoning steps were taken.
  • Data residency and access. All source material must stay within the organization's existing data boundary, with access rules respected at query time.
  • Human review. The system supports decisions but does not make them. Reviewers need a clear place to verify or overturn an answer.
  • Source freshness. Policy documents change. The system must reflect the version that was authoritative at the time of the query.
  • No unsupported confidence. The system must abstain or escalate rather than produce a plausible answer that cannot be grounded.

Approach

We would begin with a short assessment phase rather than a build. The assessment exists to answer four questions before significant investment is committed: what tasks the system is actually for, what source material it will draw on, what counts as a correct answer, and who is responsible for reviewing the output.

Task definition first

Rather than open-ended question answering, the first release would be scoped to a small number of well-defined task types — for example, summarising the current policy position on a specific topic, or locating the precedent for a particular kind of case. Narrow scope makes evaluation feasible and makes it possible to say clearly what the system does and does not do.

Evaluation before model selection

A small, curated test set would be assembled with the team: real questions, with the answers that the most experienced reviewers would consider correct, and the passages that support them. This set becomes the measurement device for every subsequent decision, including model choice. Choosing a model without it would be guessing.

Retrieval as the centre of the system

The quality of the answer depends far more on the quality of retrieval than on the specific language model used. Retrieval would be built with hybrid search across the corpus, tuned against the evaluation set, with versioning so that a query can be answered against the policy that applied at the time it was asked.

Review as a first-class feature

The interface would be designed around the review step rather than the query step. Reviewers see the answer, the passages it was drawn from, and any uncertainty signals, and can accept, modify, or reject with a recorded reason. The review decision becomes part of the audit trail.

Conceptual solution

The system would be organised in four layers, each with a clear responsibility. This separation is deliberate: it keeps the retrieval logic testable in isolation, keeps the evaluation harness independent of any particular model, and makes the audit trail a first-class part of the architecture rather than a reporting feature bolted on at the end.

Experience Reviewer interface, query, review actions
Orchestration Task routing, prompt construction, abstention
Retrieval & evaluation Hybrid search, ranking, scoring, regression sets
Platform Versioned corpus, access control, trace store

Two design choices are worth naming explicitly. First, the corpus is versioned, not just indexed: a query can be answered against the state of the sources at a particular point in time, which matters for audit. Second, the abstention behaviour is not an error case but a normal outcome: when retrieval is weak, the system says so and escalates rather than generating.

Implementation considerations

Several practical decisions would shape the delivery sequence. These are the ones we would expect to spend the most time on.

  • Corpus curation. Not every internal document belongs in the system. Working with the operating team to decide what is authoritative, and what should remain outside the boundary, is slow but essential work.
  • Evaluation ownership. The evaluation set has to be maintained by people who understand the domain. We would build the tooling and provide the initial set; the long-term ownership belongs inside the organization.
  • Human review design. The most important interface in the system is the one that lets reviewers accept, modify, or reject an answer. Getting this workflow right is what makes the system usable rather than novel.
  • Model portability. The evaluation harness makes it possible to change model providers without a loss of measured quality. Providers change; the task does not.
  • Operational telemetry. Query volume, abstention rate, review outcomes, and evaluation scores would all be visible to the operating team from the first release.

Trade-offs

Every system involves choices that are better in one dimension and worse in another. The ones below would be stated explicitly at the start of the engagement.

  • Scope over coverage. A narrow first release is easier to evaluate and safer to operate, but it does less. We would rather ship a small system the team trusts than a broad one they learn to work around.
  • Abstention over fluency. The system will sometimes say it does not know. That is a design choice, not a failure, and it costs some of the perceived usefulness that a more confident system would have.
  • Review friction over speed. Requiring a human review on every answer slows the workflow down compared to a system that answers directly. In a regulated context, that friction is what makes the output usable.
  • Provider neutrality over optimisation. Building against a single provider's features would produce a slightly better result in the short term. The evaluation harness is designed so that this is a reversible decision.

What this concept is not

It is worth being explicit about the boundaries. This document is a demonstration concept, not a project report.

  • It does not describe a real client, industry, or organization.
  • No specific business outcomes, cost savings, or accuracy figures are claimed.
  • The architecture shown is representative, not a specification to be copied.
  • Any model, provider, or tooling references are illustrative; the specific technologies would be chosen during the assessment phase against the evaluation set.
